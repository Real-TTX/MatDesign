Versions and updating

MatUi has a version of its own, with semantic versioning: a patch fixes something, a minor adds something, a major needs work in the app. A version that breaks something says so in the changelog and says what to do.

This version
0.1.0, built by MatDesign local-20261014
What changed
The changelog, or as a file /ui/CHANGELOG.md, or as data /api/changelog (?since=0.1.0 gives what an app on 0.1.0 takes with an update)
For a program
/ui/manifest.json: the version and every file with its SHA-256; the archive carries it as matui.manifest.json
Check an app
node tools/matui-check.js <folder of the app> finds its copy of MatUi, says which version it is, whether files were changed by hand and what an update takes with it
How it works
docs/VERSIONING.md: what is a breaking change, how a version is made and how an app updates

Use it

Put the files into the static files of the app. The layout needs one stylesheet, a boot script in the head, a script at the end and the sprite inline. The skeleton of a whole page is on the shell page.

<html lang="en" data-app="yourapp">
<head>
  <script src="/matui.boot.js"></script>
  <link rel="stylesheet" href="/matui.css" />
</head>
<body>
  <!-- the contents of matui-icons.svg, inline, once -->
  ...
  <script src="/matui.js"></script>
</body>
</html>

/* your own CSS: the colour of the app, nothing else */
[data-app="yourapp"] { --mat-app-accent: #2f6feb; }

In a .NET solution reference the MatUi project (a Razor class library). Its files are served below /_content/MatUi/; the sprite is read and written into the layout once.

<!-- App.csproj -->
<ProjectReference Include="..\MatUi\MatUi.csproj" />

<!-- _Layout.cshtml, in the head -->
<script src="~/_content/MatUi/js/matui.boot.js"></script>
<link rel="stylesheet" href="~/_content/MatUi/css/matui.tokens.css" />
<link rel="stylesheet" href="~/_content/MatUi/css/matui.base.css" />
<!-- ... shell, controls, forms, pickers, lists, dialogs, layout, apps in this order -->

<!-- at the end of the body -->
<script src="~/_content/MatUi/js/matui.js"></script>

The design system as data

For tools, tests and other apps that want to read the rules, the accents or the tokens instead of copying them.

Data endpoints
AddressWhat it returns
/api/appsThe apps: id, name, category, accent, text colour on it, glyph, port.
/api/accentsThe accents a user can choose in the settings.
/api/schemesThe colour schemes: id, name, and the tokens each sets in light and in dark.
/api/rulesThe whole rulebook: id, area, title, statement, level, source.
/api/tokensEvery design token with its light and dark value.
/api/propertiesThe documented component properties (--mat-btn-radius ...): component, name, type, the default it falls back to and what it changes.
/api/iconsThe names of the icons in the sprite.
/api/iconlibThe icon library: its categories, and every icon with its categories and tags.
/api/versionThe version of the toolkit (matui), the build of the site and the hash of the files.
/ui/manifest.jsonThe version, the build and every file of the toolkit with its SHA-256: what a program compares with an app's copy.
/ui/CHANGELOG.mdWhat changed in each version, as the file.
/api/changelogWhat changed, as data: all versions, or those after ?since=0.1.0, with their sections and migration steps.
